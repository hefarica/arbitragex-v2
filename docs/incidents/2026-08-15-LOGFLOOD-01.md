# Incidente LOGFLOOD-01 — Flood de logs cartridge + debugging a ciegas (+ BOOT-HANG)

**Fecha:** 2026-08-15 (~21:03–22:30 UTC)
**Severidad:** Observabilidad degradada (LOGFLOOD-01) + feed de detección mempool muerto (BOOT-HANG, ver §8)
**Estado:** LOGFLOOD-01 CERRADO (`e557fd95`) · BOOT-HANG mitigado con timeouts+marcadores (parche operador, commit ver PR #338)

## 1. Síntoma reportado

"El scanner está colgado; cero eventos de detección": ausencia de
`scanner.orchestrator_mode`, `mempool_mode_resolved`, `connected`, `subscribed`
y `no_rpc` en `docker logs arbitragex-v2-searcher-rs-1`.

## 2. Hipótesis inicial (PARCIALMENTE INCORRECTA)

`run_chain` colgado en un await sin timeout. La parte cierta: la construcción
boot SÍ carece de timeouts (hydrate O(N) sin per-command timeout — redis-rs
ConnectionManager no timeoutea respuestas colgadas). La parte errónea de mi
sesión inicial: concluir "pipeline vivo de punta a punta" a partir de greps
artefactuales (ver §3).

## 4. Causa raíz del ciego (LOGFLOOD-01)

`cartridge.active_eval_negative` a **INFO por-cartucho-por-intent** (~269 ×
~0.7 intents/s ≈ **183 líneas/s ≈ 1.6 GB/día**). Rotación docker
`max-file:5 × max-size:10m` = **50MB** → ventana evaporada en ~10 min: boot
lines incluidas. Contenedor iniciado 21:03:55; primera línea retenida
21:36:34. Todo grep de "evento ausente" leyó una ventana amnésica.

## 5. Fix LOGFLOOD-01 (`e557fd95`)

Negativos per-cartridge → `debug!`; UN `cartridge.active_eval_summary` a INFO
por intent con histograma de razones (BTreeMap, R8: preservadas). Validado 7/7
(reachability: todas las salidas internas del loop son `continue`). Ventana de
logs ~10 min → ~18 h.

## 6. Gates anti-repetición

1. **R9 (CLAUDE.md §3):** verificar ventana (`docker inspect` LogConfig +
   StartedAt vs primera línea retenida) ANTES de concluir "evento ausente".
2. **Regla de logging:** hot-loops per-ítem a `debug!` + summary agregado
   `info!` (patrón de 6aba8f6c).
3. **Heartbeat como fuente autoritativa** de salud del pipeline
   (`pending_received`/`decoded_ok`), no greps de presencia.
4. Índice PG `idx_opp_detected_at` + retención 30d (`scripts/pg_retention.sh`)
   — PGBLOAT-02: 15.8M filas / 6.9GB / 7.57M >30d archiveadas y purgadas.

## 7. Lecciones

- La ausencia de un evento en `docker logs` NO prueba nada con rotación
  agresiva. Verificar la ventana primero (R9).
- Un loop honesto (R8) que emite 183 líneas/s destruye la observabilidad del
  resto — el volumen ES un incidente.
- Un grep de presencia puede matchear subcadenas de campos (`decoded_ok`) y
  "probar" lo falso. Discriminar por valor de evento exacto.
- Correr los discriminantes baratos (canal de error del supervisor, heartbeat)
  ANTES de teorizar sobre deadlocks.

## 8. BOOT-HANG (paralelo, teoría del operador — validada como riesgo real)

El boot de `run_chain` no tiene timeouts: `fetch_all_enabled_chains` (PG),
`build_http_pool`, `hydrate_from_redis` (SCAN + GET secuencial por key sobre
`arbx:pool_reserves:1:*`, keyspace que crece todo el día con pool_sync),
pool_map, `ImpactIndex::from_registry` (JOIN 4 tablas), `build_orchestrator`.
Cualquier stall ahí = `detection_loop` nunca spawnea = `pending_received: 0`
para siempre, con el resto del sistema aparentemente sano. El patrón
histórico (contenedor 02:16 detectaba; 19:24+ ya no) es consistente con
hidratación O(N) que cruzó la ventana de paciencia.

**Mitigación (parche operador, 2 archivos):** timeout 10s/30s en supervisor
(PG read + build_http_pool → `None`), timeout 30s hydrate / 30s pool_map /
120s ImpactIndex / 180s build_orchestrator → **fail-open** (detection_loop
arranca sin orchestrator — shape ya ejercitada por V1/Off), marcadores de fase
`run_chain_entered` → `ws_pool_built` → `orchestrator_build_start` →
`detection_loop_entered` + eventos `*_timeout` que nombran al culpable.

**Discriminante pendiente post-deploy:** si con `detection_loop_entered` +
`orchestrator_present=true` el heartbeat sigue en `pending_received: 0`, el
responsable es la **suscripción WS de pending txs** (no el boot) → siguiente
anomalía. El pipelining de `hydrate_from_redis` (MGET por lotes) queda como
PR de perf recomendado.
