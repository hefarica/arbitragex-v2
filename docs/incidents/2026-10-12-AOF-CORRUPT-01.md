# Incidente 2026-10-12 — AOF-CORRUPT-01: redis crash-loop por AOF truncado, origen HTTP caído ~3h

## TL;DR

Un evento de stack a las **00:43** interrumpió un AOF rewrite de redis en vuelo.
El archivo incremental quedó truncado y redis entró en crash-loop
(`Bad file format reading the append only file`). Todo servicio con
`depends_on: redis: service_healthy` quedó clavado — el api-server quedó en
estado `Created` y el origen HTTP sirvió **500 en todas las rutas** (~3h).
Postgres sufrió el mismo evento (RestartCount 8) pero se recuperó solo con su
WAL recovery; redis no tiene equivalente automático. Esa asimetría es la que
este gate corrige.

## Causa raíz

Cola truncada de `appendonly.aof.11378.incr.aof` (3.111.769 bytes descartados
por `redis-check-aof --fix`, `ok_up_to=3637616`). El evento que interrumpió el
rewrite coincidió con reinicio de postgres (mismo minuto) — sin trazas de OOM
en kernel log accesible. **Segunda corrupción de AOF del mes** (primera:
2026-09-23 disk-full, `appendonly.aof.4975.incr.aof.bak-diskfull-20260923`).

## Gates que nacen de este incidente

1. **`redis-aof-guard` (ARBX-AOF-GUARD-01)** — servicio init one-shot en
   `docker/compose.prod.yml` + `docker/compose.dev.yml`; valida cada parte AOF
   antes del boot de redis, respalda y repara colas truncadas
   (`redis-check-aof --fix`), purga sus backups >7 días, y hace pass check-only
   sobre las bases RDB (un RDB corrupto no tiene herramienta de repair: se
   loggea fuerte para acción del operador). **FAIL-OPEN**: nunca bloquea el
   boot de redis por falla propia del guard.
   Script: `docker/redis-aof-guard.sh`.
2. **`ApiServerScrapeDown`** — `monitoring/alerts.rules.yml`. Misma lección H2b
   que `SEARCHER_SCRAPE_DOWN`: `arbx_service_up` solo hace set(1) y no ve un
   api-server muerto; el `up{job="api-server"}` nativo del scrape sí estuvo en
   0 toda la outage sin regla que lo gritara.
3. **Host sysctl** — `vm.overcommit_memory=1` (warning de redis en cada boot:
   fork de BGSAVE/BGREWRITEAOF puede fallar bajo presión de memoria; un fork
   fallado a mitad de rewrite es un productor de exactamente este incidente).
   Aplicado en vivo y persistido en `/etc/sysctl.d/99-arbx-redis.conf` el
   2026-10-12.

## Deuda visible que este incidente expuso (NO cerrada aquí)

- **Alertmanager entrega al edificio en llamas**: el único receiver activo es
  `webhook → api-server:8080/admin/alertmanager/webhook`. Cuando el origen
  muere, las alertas (que SÍ dispararon: `HighHTTP5xxRate firing`) no llegan a
  nadie. Los receivers externos están deshabilitados por diseño. Decisión de
  canal (email/telegram/webhook externo) = operador.
- **`edge:8787/metrics` scrapea `down`** (el edge sirve HTTP 200 pero no
  expone `/metrics`): las reglas basadas en métricas del edge no tienen
  productor.
- Redis no expone `/metrics` (sin redis_exporter): la salud de redis solo es
  visible por su blast radius (api-server scrape + 5xx).

## Verificación del gate

- Falsificación: copia del `appendonlydir` truncada a propósito en volumen
  temporal → el guard la repara en un pass (ejecutado post-deploy, ver
  runbook abajo).
- `docker compose config` valida ambos composes.
- `bash -n docker/redis-aof-guard.sh` limpia.
