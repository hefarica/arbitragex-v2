# Incidente 2026-10-12 — AOF-CORRUPT-01: redis crash-loop por AOF truncado, origen HTTP caído ~3h

## TL;DR

Un evento de stack a las **00:43** interrumpió un AOF rewrite de redis en vuelo.
El archivo incremental quedó truncado y redis entró en crash-loop
(`Bad file format reading the append only file`). Todo servicio con
`depends_on: redis: service_healthy` quedó clavado — el api-server quedó en
estado `Created` y el origen HTTP sirvió **500 en todas las rutas** (~3h).
Postgres sufrió el mismo evento (RestartCount 8) pero se recuperó solo con su
WAL recovery; redis no tiene equivalente automático. Esa asimetría es la que
este gate corrige.

## Causa raíz

Cola truncada de `appendonly.aof.11378.incr.aof` (3.111.769 bytes descartados
por `redis-check-aof --fix`, `ok_up_to=3637616`). El evento que interrumpió el
rewrite coincidió con reinicio de postgres (mismo minuto) — sin trazas de OOM
en kernel log accesible. **Segunda corrupción de AOF del mes** (primera:
2026-09-23 disk-full, `appendonly.aof.4975.incr.aof.bak-diskfull-20260923`).

## Gates que nacen de este incidente

1. **`redis-aof-guard` (ARBX-AOF-GUARD-01)** — servicio init one-shot en
   `docker/compose.prod.yml` + `docker/compose.dev.yml`; valida cada parte AOF
   antes del boot de redis, respalda y repara colas truncadas
   (`redis-check-aof --fix`), purga sus backups >7 días, y hace pass check-only
   sobre las bases RDB (un RDB corrupto no tiene herramienta de repair: se
   loggea fuerte para acción del operador). **FAIL-OPEN**: nunca bloquea el
   boot de redis por falla propia del guard.
   Script: `docker/redis-aof-guard.sh`.
2. **`ApiServerScrapeDown`** — `monitoring/alerts.rules.yml`. Misma lección H2b
   que `SEARCHER_SCRAPE_DOWN`: `arbx_service_up` solo hace set(1) y no ve un
   api-server muerto; el `up{job="api-server"}` nativo del scrape sí estuvo en
   0 toda la outage sin regla que lo gritara.
3. **Host sysctl** — `vm.overcommit_memory=1` (warning de redis en cada boot:
   fork de BGSAVE/BGREWRITEAOF puede fallar bajo presión de memoria; un fork
   fallado a mitad de rewrite es un productor de exactamente este incidente).
   Aplicado en vivo y persistido en `/etc/sysctl.d/99-arbx-redis.conf` el
   2026-10-12.

## Deuda visible que este incidente expuso (NO cerrada aquí)

- **Alertmanager entrega al edificio en llamas**: el único receiver activo es
  `webhook → api-server:8080/admin/alertmanager/webhook`. Cuando el origen
  muere, las alertas (que SÍ dispararon: `HighHTTP5xxRate firing`) no llegan a
  nadie. Los receivers externos están deshabilitados por diseño. Decisión de
  canal (email/telegram/webhook externo) = operador.
- **`edge:8787/metrics` scrapea `down`** (el edge sirve HTTP 200 pero no
  expone `/metrics`): las reglas basadas en métricas del edge no tienen
  productor.
- Redis no expone `/metrics` (sin redis_exporter): la salud de redis solo es
  visible por su blast radius (api-server scrape + 5xx).

## Verificación del gate

- Falsificación: copia del `appendonlydir` truncada a propósito en volumen
  temporal → el guard la repara en un pass (ejecutado post-deploy, ver
  runbook abajo).
- `docker compose config` valida ambos composes.
- `bash -n docker/redis-aof-guard.sh` limpia.

## Addendum 2026-10-12 (post-deploy) — verificación en producción y dos hallazgos operativos

### El guard ya trabajó en prod (primera corrida real)

El deploy de `560da2ca` recreó redis; el guard corrió como init y la evidencia
del contenedor (no de un documento):

| Artefacto | Valor medido |
|---|---|
| `docker ps -a \| grep redis-aof-guard` | `Exited (0) 4 minutes ago` |
| `docker logs arbitragex-v2-redis-aof-guard-1` | `all AOF incr files OK` (05:16:39Z) |
| redis post-recreate | `PONG`, `XLEN arbx:opps:detected = 10000` |
| control-plane preservado | `GET arbx:killswitch` = `{"enabled":false,…}` (A5-STALL intacto) |

El modo de fallo del incidente (AOF truncado → redis crash-loop → api-server
`Created` → 500 en todo) ahora se auto-repara en boot.

### Hallazgo 1 — Reglas de Prometheus: bind mount de ARCHIVO = inodo congelado

Agregar `ApiServerScrapeDown` al rules file **no basta**: tras el `git pull`,
`grep` en el HOST ve la regla (1) pero dentro del contenedor no (0), y
`stat -c %i` da inodos distintos (host `281962` vs contenedor `272229`).
`POST /-/reload` responde 200 (`--web.enable-lifecycle` está activo) y **aun
así la regla no carga**: Prometheus relee el mismo inodo viejo.

- **Regla operativa:** todo cambio a `monitoring/alerts.rules.yml` exige
  `docker compose --env-file .env -f docker/compose.prod.yml up -d --force-recreate prometheus`
  después del pull. Un deploy normal NO recrea prometheus (su spec no cambió) →
  la regla queda sin cargar en silencio.
- Aplica a cualquier archivo montado individualmente que cambie sin cambio de
  compose.

### Hallazgo 2 — Route discovery: `/api/quote/anchor` y `/api/route-discovery/tick` tras 24h de uptime

Los dos wires 503ean honestamente (`quote_anchor_not_published`,
`tick_not_available`) y la cadena de causa quedó medida de punta a punta:

1. El writer existe y está habilitado: `route_discovery_worker.rs:1189` llama
   `write_quote_anchor_snapshot` ("runs every tick"); `ARBX_ROUTE_DISCOVERY_MODE=shadow`
   en el env del contenedor y en `.env`.
2. No hay clock skew (container == host == 05:23:03Z).
3. El stream `arbx:route_discovery:outcomes` (150.002 entradas, `entries-added`
   1.029.813.167) está **vivo** (última entrada 05:21:36Z) pero cada outcome
   declara `reason= snapshot_stale_or_clock_skew`, `had_reserves=false`,
   `context_provenance=static_boot_stub`, `v4_repairs.status=DATA_GAP`.
4. La condición exacta: `snapshot_services.rs:196-198` —
   `now > data.valid_until_ms` ⇒ `snapshot_stale_or_clock_skew`. El
   `SnapshotBundle` de boot (`cartridge_boot.rs:207`, `boot-genesis-*`) tiene
   **validez 24h**; el searcher corría desde Oct 9 13:19 → bundle expirado hace
   ~40h.
5. Consecuencia: evaluación shadow sin reserves → `edges_built=0` /
   `routes_found=0` → sin token scoreable → selección `None` → anchor y tick
   snapshot nunca publicados → 503 (R8 honesto, no bug de la ruta).
6. **No es un defecto de wiring**: el comentario in-code declara que los
   producers del bundle real son fases posteriores ("issue #647 family"). El
   propio fix de boot está documentado por diseño: *"a restart rebuilds it
   fresh"*.

**Acción:** el restart del searcher (deploy en curso) reconstruye el bundle
fresco por 24h. El cierre real es el producer del bundle por-intent
(issue #647 family) — su card propia, no un parche de proximidad.

### Falsa alarma descartada con aritmética (R9 sobre el propio conteo)

`pool_sync.redis_set_failed` apareció 41.453 veces en la ventana de log
(02:55→05:15Z) y parecía un fallo continuo de escritura. La muestra del error
era `BusyLoadingError: Redis is loading the dataset in memory` con timestamp
**03:41:06Z** — la ventana del fix manual de redis. Aritmética: 41.453 fallos /
453 ticks ≈ 91 SETs por tick, consistente con **ráfagas durante las ventanas de
carga** de redis (03:41 fix, 05:16 recreate), no con fallo sostenido. En los
últimos 3 minutos: **0** fallos; memoria 303M/1G; `SET → OK`. Conclusión: R9
aplicada al propio conteo antes de abrir un incidente falso.
