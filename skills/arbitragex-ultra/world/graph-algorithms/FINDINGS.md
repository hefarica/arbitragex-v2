# Graph algorithms for AMM/DEX arbitrage route discovery (2024-2026 state of the art): negative-cycle detection, cycle enumeration, convex-optimization multi-pool routing, graph pruning, incremental updates, and route ranking under staleness/adverse selection.

## Findings

UNIVERSAL FOUNDATION: every serious system (and ArbitrageX's own Excel marginal prefilter) uses the log transform w(u,v) = -log(r(u,v)) (fee-adjusted: -log((1-fee)*rate)), so a profitable cycle satisfies sum_e w_e < 0 iff product of rates > 1. All six research areas are downstream of this representation.

=== 1. NEGATIVE CYCLE DETECTION ===

(a) Bellman-Ford family. Bellman-Ford-Moore (BFM) O(n*m) with "walk-to-the-root" cycle extraction is the classic baseline (DeFi-ARB, the first systematic DEX arb detector, used BFM). Goldberg-Radzik (GOR) remains the practical champion: the SEA 2025 algorithm-engineering study (Cassis, Karrenbauer, Nusser, Rinaldi, "Algorithm Engineering of SSSP with Negative Edge Weights", https://drops.dagstuhl.de/storage/00lipics/lipics-vol338-sea2025/LIPIcs.SEA.2025.10/LIPIcs.SEA.2025.10.pdf, code https://github.com/PaoloLRinaldi/negative_weight_SSSP, full version https://arxiv.org/abs/2502.11999) implemented the first practical version of the near-linear-time negative-weight SSSP algorithms (Bernstein-Nanongkai-Wulff-Nilsen FOCS 2022; Bringmann-Cassis-Fischer FOCS 2023, ~O(m polylog n)). Result: GOR is 5.4-7.1x FASTER than the near-linear implementation on ordinary instances (DIMACS road graphs, random graphs up to 2*10^7 edges), BUT the near-linear implementation is ~2 orders of magnitude faster on adversarial instances (BAD-GOR: 0.95s vs 720s at 10^6 edges). Lesson: for production DEX graphs, GOR-style label-correcting is the right default; near-linear methods buy worst-case robustness against pathological weight structures. Caveat: all these detect EXISTENCE of a negative cycle, not the k-hop MOST negative cycle, and handle hop constraints poorly (RICH's central criticism).

(b) RICH (VLDB 2025) - the current SOTA for arbitrage cycle detection. Luo et al., "RICH: Real-time Identification of negative Cycles for High-efficiency Arbitrage", PVLDB 18(11):4081-4089, doi:10.14778/3749646.3749678 (https://www.vldb.org/pvldb/vol18/p4081-luo.pdf, code https://github.com/Xtra-Computing/RICH). Built with Tokka Labs (40+ on-chain venues). Formulates the k-hop Most Negative Cycle (kMNC) problem: find argmin over simple cycles of exactly k hops of sum of w_e - proven NP-complete/NP-hard. Algorithm: (1) color-coding (Alon-Yuster-Zwick 1995): assign each vertex a random color in {1..k}; only "multicolored" paths are explored - a multicolored k-cycle is automatically simple; the optimal cycle gets distinct colors with probability k!/k^k per instance, so omega instances give detection probability 1-(1-k!/k^k)^omega (k=4, omega=50 -> 99.27%; k=5, omega=30 -> <5% relative error on all datasets). (2) Held-Karp-style DP: state dp[v][color-set] = min weight path ending at v using that color set; transition dp[u][S'|] = min(dp[u][S'], dp[v][S]+w(v,u)); complexity O(2^k * |V| * |E|) per instance, memory O(|V| * 2^k). (3) Bitwise color-set encoding: colors as k-bit integers, membership check via AND, insertion via OR - O(1) instead of O(k); removing it slows RICH 52.6-90.3%. (4) Color-guided graph reduction: iteratively delete nodes whose only valid neighbor shares their color (safe by Lemma: such a node cannot be on a multicolored cycle) - removes >20% of nodes; worth 2.2-9.8% runtime. Benchmarks on Uniswap V2 token graphs (UNI1-UNI6: 11.6K-359.6K nodes, 27.2K-734.1K edges, avg degree ~4.1, max degree up to 354K): RICH 0.94s (UNI1) to 47.52s (UNI6); speedups vs second-best 1.6x-32.69x; vs DFS-based BriDe 31.6x-176.2x at k=5 and 330x-2194x at k=6; relative error vs exact enumeration 0.02%-3.90%; memory <2.3GB worst case. Within 15s RICH finds a cycle >45% more negative than competitors stuck in local optima. vs bounded DFS: DFS-with-vertex-removal is only competitive at k=3; at k>=5 its redundant path re-exploration explodes exponentially while RICH's DP stays O(2^k*m). Justification for k<=5: cycles longer than 5 hops are <2% of crypto-market arbitrage cycles (GoldPhish and cyclic-arb studies cited in RICH).

(c) Incremental/dynamic. Theory exists: Demetrescu-Italiano fully-dynamic APSP with O(n^2) amortized update for real weights (no negative cycles) (http://www.dis.uniroma1.it/~demetres/docs/dapsp-full.pdf); Adaptive Bellman-Ford re-detects negative cycles after edge-weight changes without full recomputation (Chandrachoodan et al., ISCAS 2001, http://sig.umd.edu/publications/Chandrachoodan_ISCAS_200105.pdf). But the telling fact: RICH - the best 2025 academic system - explicitly lists "support for dynamic or streaming graphs" as FUTURE WORK; it rebuilds per block. So the practical SOTA is "stable topology + per-block weight refresh", not theoretical dynamic SSSP.

=== 2. CYCLE ENUMERATION ===

Johnson's algorithm enumerates ALL elementary cycles in O((n+m)*c) where c = number of simple cycles - output-polynomial but c can be exponential; and per RICH's related-work analysis, enumeration indexes are pointless for arbitrage because "the set of tokens and trading pairs is stable over short periods, but edge weights change rapidly... making cycle weight computation the main bottleneck". Enumerate-once-then-score is dominated by search-that-uses-weights. Bounded DFS (depth<=k, prune repeated vertices, optionally vertex-removal after each root) is the practitioner default (BriDe 2024; GoldPhish 2023 uses greedy traversal with pivot-token and cycle-length heuristics); its failure mode is local-optimum trapping: RICH Figure 2 shows DFS/greedy methods plateauing at suboptimal weights for 40+ seconds while color-coding's randomized global restarts escape. The winning enumeration paradigm 2024-2026 is color-coding (FPT in k, O(2^k*m) per instance, anytime-improvable by adding instances). A different enumeration direction: arXiv:2406.16573 "An Improved Algorithm to Identify More Arbitrage Opportunities on DEXs" (https://arxiv.org/html/2406.16573v1) builds the LINE GRAPH L(G) (edges->vertices, |V_L|=|E|, |E_L| = sum d_i^2 - 2|E|), adds a super-source linked to the source token's edges, and runs modified MBF (MMBF) with a path-repetition constraint: one run per source token yields 1 loop per token PLUS non-loop negative s-t paths (N loops and N^2 paths total). Result on Uniswap V2 (Sep 2020-Oct 2023): 23,868 paths with profit >$1,000 vs 19 for plain MBF; path lengths 7-11 vs 3-4; max observed profit ~$1M vs ~$100K; ~8-10s per graph of ~100 tokens/~400 pools. Optimal trade size via bisection on the concave output function (dΔy/dΔx = 1 at optimum for loops). This is the concrete evidence that non-cyclic negative paths are a large unexplored surface that cycle-only detectors miss.

=== 3. MULTI-POOL ROUTING AS CONVEX OPTIMIZATION ===

(a) Angeris, Evans, Chitra, Boyd, "Optimal Routing for Constant Function Market Makers" (EC'22, https://arxiv.org/abs/2204.05238, https://dl.acm.org/doi/10.1145/3490486.3538336): network routing across CFMMs formulated as a convex program (trading functions concave -> convex feasible set; self-financing constraints via token-flow matrix T; maximize utility of net trade Psi). Arbitrage is the special case Psi>=0. Solvable to GLOBAL optimality - the definitive answer to "which cycle and how to split": no enumeration at all, the optimizer chooses route shape and splits jointly.

(b) Diamandis, Resnick, Chitra, Angeris, "An Efficient Algorithm for Optimal Routing Through CFMMs" (FC 2023, https://arxiv.org/abs/2302.04938): decomposition method - dual decomposition/ADMM-family; each CFMM solves a small closed-form single-market arbitrage subproblem in parallel, a master problem enforces token conservation; per-iteration cost is embarrassingly parallel. Dramatically outperforms Mosek (commercial conic solver) as pool count grows and returns >50% HIGHER objective (interior-point solvers stop strictly inside the trading set, but optimal trades always sit on the boundary). Handles "aggregate CFMMs" - a whole Uniswap V3 pool with all its ticks collapsed into one concave output function - natively in the subproblem interface. Production code: CFMMRouter.jl (https://github.com/bcc-research/router-experiments). On-chain demo: routing WETH->USDC split across USDC-WETH 0.3%, WETH-USDT 0.3%, USDC-USDT 0.01% beats the single direct pool by an increasing margin as size grows. Paper explicitly flags robust routing (state changed by earlier txs) and gas-aware activation as open problems - both since attacked (below).

(c) Bancor/Carbon "Marginal Price Optimization" (Loesch & Richardson, Feb 2025, https://arxiv.org/abs/2502.08258, productized as Arb Fast Lane, https://bancor.network/arbfastlane, open-source bot https://github.com/bancorprotocol/fastlane-bot): KEY INNOVATION - reduce dimensionality from 2 variables per curve to 1 variable per TOKEN: optimize the price vector pi in R^N; each curve responds via a "price response function" mapping target marginal price to required trade; solution = equalize marginal prices across all curves touching a pair + circularity (product of marginal prices around any loop = 1, i.e., p_marg(i,j) = pi_i/pi_j). Equivalent to the convex formulation except at infinite concentration (Thm 19). Numerics: bisection + damped Newton-Raphson on the N-dimensional system. Motivation: convex solvers FAIL TO CONVERGE on levered (concentrated-liquidity) curves - concrete case: two levered curves, ~$17 obvious profit, no CVXPY solver converged until an unlevered sentinel curve was added. Result: up to 200x faster than Clarabel (CVXPY default), robust on levered curves without sentinels; scales to 1,000-curve markets. Also defines the "Repatriation Problem" (choosing which token to extract profit in) and handles limit orders as infinite-leverage limit with imputed minimum width. This is what a 2025 production arbitrage engine actually runs.

(d) Xi & Moallemi (Columbia GSB, Jul 2026, "Quantifying Sub-Optimality in Routing for AMMs", https://arxiv.org/abs/2607.20762): exact bisection algorithm for same-pair multi-pool routing: define inverse marginal price mp_j^{-1}(lambda) = inf{q>=0 : mp_j(q) >= lambda}; S(lambda) = sum_j mp_j^{-1}(lambda) is monotone, so the KKT marginal-equalization condition (all ACTIVE pools share marginal price lambda*, inactive pools have weakly higher) is solved by bisecting S(lambda*) = Q - unique, exact, machine-precision (works for CPMM and concentrated liquidity). Gas handled by an activation model: fixed cost g_j paid iff q_j>0, cleanly separating the combinatorial pool-subset choice from the continuous split (preserving concavity). Their three benchmarks (SCO = split quality on pools actually used; FVO = all venues, no gas; G-FVO = gas-aware) audited 2.98M WETH-USDC swaps: average routing shortfall 2.02 bps/trade = $24M over ~$120B volume.

(e) Production split routing: Uniswap Smart Order Router (https://github.com/Uniswap/smart-order-router, https://blog.uniswap.org/auto-router-v2) splits across V2/V3 pools and routes with gas-aware search; every major aggregator (1inch, etc.) does single-pair split + multi-hop search.

vs bounded DFS: convex/marginal-price methods answer a DIFFERENT and strictly stronger question - "given all pools simultaneously, what is the globally optimal split?" - while bounded DFS enumerates candidate paths and then sizes ONE path. The academic results show path-then-size leaves 2+ bps on the table and greedy/DFS misses the most-negative cycles; the optimizers also natively cover split routing, V3 tick aggregation, and directional/limit liquidity that path enumeration handles awkwardly.

=== 4. GRAPH PRUNING ===

Standard production discipline, best documented in arXiv:2406.16573: keep pools with TVL > $20K active that day; iteratively remove degree-1 tokens; prune to ~100 tokens/~400 pools covering ~90% of TVL; cut mutual 2-token round-trip edges in the line graph (never profitable). Hub-token identification: restrict pivots to high-liquidity "hubs" (WETH, stables) - GoldPhish's heuristic and every practitioner writeup (e.g., https://x.com/0xSarthak13/status/2056803366530105731: "the hubs, because that's where the majority of liquidity exists; pruning dead-end tokens entirely"); curated token lists (Uniswap default list) act as de facto hub sets. RICH contributes color-guided reduction (same-color single-neighbor pruning, >20% node removal). Notably, k-core decomposition for DEX arb graphs appears UNDEREXPLORED academically (my search found no direct combination) - an open, cheap win: peeling the (k>=2)-core removes dangling token trees before cycle search; equivalently a liquidity-weighted core. The empirically important structure: Uniswap token graphs have avg degree ~4.1 but max degree in the hundreds of thousands (star topology around hubs), so pruning is about killing the star's dead spokes, and cycle search survives on the dense hub core.

=== 5. EVENT-DRIVEN INCREMENTAL UPDATES VS PER-BLOCK REBUILDS ===

SOTA pipeline (RICH/Tokka Labs, confirmed as the industry pattern): per new block (12-15s Ethereum): rebuild weights -> detect -> execute -> iterate. Structure (tokens, pools) is stable over short horizons; only edge weights move - so the graph object is persistent and weights are refreshed. Event-driven layer: amms-rs (https://github.com/darkforestry/amms-rs, crates.io `amms`) is the production Rust library for exactly this: discover AMMs by factory, sync state once, then subscribe to real-time events (Sync for V2 reserves, Swap/Burn/Mint for V3 ticks) over WebSocket to keep reserves live without re-querying; searcher frameworks (artemis, https://github.com/paradigmxyz/artemis; write-ups like https://hotpath.rs/blog/rust-mev-bot) do the same for mempool/pending-tx anticipation. Why not theoretical dynamic SSSP (Demetrescu-Italiano etc.)? Negative-cycle maintenance under arbitrary weight updates lacks practical implementations, and graphs are small enough (<=1M edges) that refresh-and-research dominates. The sophisticated middle ground used in practice: (i) persistent adjacency + in-place weight writes; (ii) cycle-edge inverted index - only cycles containing changed edges are re-validated on a Sync event; (iii) mempool simulation to pre-apply pending swaps to a shadow state (execute against the post-pending-block world). The 2026 Columbia audit gives the economic justification for freshness: optimizing on 1-block-lagged state instead of execution-time state raises mean shortfall by 1.29 bps (FVO, ~$15.5M in sample) / 1.78 bps (G-FVO, $21.4M); further lag continues to hurt with diminishing increments; and realized routes evaluated on PRE-execution snapshots look closer to optimal - proving timing mismatch (stale planning state), not algorithmic error, is the dominant loss source.

=== 6. ROUTE RANKING: EV SCORING, STALENESS, ADVERSE SELECTION ===

EV: rank candidates by expected net topological yield Pi_R(x) = Q_R(x) - x - C_R(x) where C_R includes gas + flash fee + decoherence; the 2406.16573 bisection (marginal output = 1) or Angeris convex program computes max_x exactly. Staleness discounting: the Xi-Moallemi numbers (1.29-1.78 bps per block of lag, heavy-tailed) give a principled decay - score routes by the freshness-weighted fraction of their edges (edges touched by recent Sync/Swap events should be treated as uncertain until re-synced; routes over stale pools get discounted, not trusted). Adverse selection: (a) the Columbia audit shows sandwich attacks drive a significant fraction of measured sub-optimality, losses are heavy-tailed, small trades lose more in %, and protection correlates with execution context - public flow (Universal Router) suffers, solver-mediated batch auctions and private order flow (CoW Swap) show negligible incidence; (b) equilibrium model of gas competition "Arbitrage on Decentralized Exchanges" (https://arxiv.org/html/2507.08302v2): most arbitrage trades use LESS than the maximum amount and high-priority gas fees are selected LESS often than low-priority ones - implying optimal bids are not "win at any cost" and sizing should account for competition probability; (c) backrun/orderflow-auction surfaces: MEV-Share (https://collective.flashbots.net/t/mev-share-programmably-private-orderflow-to-share-mev-with-users/1264, https://github.com/flashbots/mev-share) - searchers bid in an OFA for backrun rights against private flow with hints; "Do Backrun Auctions Protect Traders?" (https://arxiv.org/pdf/2401.08302) models capture probabilistically; Frontier Research's OFA design-space survey (https://frontier.tech/the-orderflow-auction-design-space) compares 12 OFAs. Ranking under competition = EV * P(win auction | bid) - bid, a game-theoretic layer on top of the deterministic Pi_R.
